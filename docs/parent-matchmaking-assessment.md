# 父母帮助子女相亲：调整评估

评估日期：2026-10-06

依据：用户提供的「刘老师」目录内 1.jpg 至 23.jpg，以及 Friends 当前前端、后端、管理端和 Prisma 数据结构

本文保留参考截图的逐项评估，并记录已确认的首版方案；首版业务代码已按该范围重构，开发验收说明见 parent-registration-development.md

## 1. 已确认的范围

- 产品从子女自行交友转向父母帮助子女相亲
- 本轮先改产品定位、注册和子女资料登记
- 保留后台资料审核和人工牵线
- 邀请码、推广二维码、邀请关系继续保留，作为选填的获客渠道
- 首版一个账号只登记一个孩子，数据结构支持以后扩展
- 首版保留手机号和密码，预留短信验证码接口，暂不接入实际短信服务
- 产品处于研发阶段，不兼容或迁移旧数据，可直接重构

## 2. 核心结论

需要把「登录账号」与「相亲对象」分开

父母用自己的手机号登录，登记孩子的条件和择偶要求，运营审核孩子的档案，牵线关联双方孩子，沟通联系人通常是父母

评估时 User 同时承载手机号、密码、昵称、性别、年龄、照片和交友要求，如果只改页面文字，会继续把父母的身份与孩子的身份混在一起

建议保留现有账号、介绍人和管理端基础，新增独立的子女档案，将审核、照片、择偶要求和牵线记录逐步迁到档案维度

## 5. 建议的注册与登记流程

采用「先回答少量问题，再绑定父母账号」的引导方式，可参考截图降低首次使用的门槛

```text
进入落地页 / 带邀请码的分享链接
  -> 说明父母为孩子登记相亲资料
  -> 选择您是父亲还是母亲
  -> 选择孩子性别
  -> 填写孩子出生信息、身高、现居城市、学历、月收入
  -> 验证父母手机号 / 创建父母账号
  -> 保存前面填写的内容为子女档案草稿
  -> 填写或跳过非必填择偶偏好与补充资料
  -> 预览并确认，提交审核
  -> 我的：孩子资料卡、审核状态、修改入口
```

将关系提前询问是调整建议，参考截图把它放在后续补充资料中

已有账号直接登录并恢复现有草稿，不因重复进入登记流程而生成第二个档案

### 登录方式的两种实现

| 方式 | 对父母的使用体验 | 开发影响 |
| --- | --- | --- |
| 短信验证码，注册与登录合并 | 不用记密码，与参考截图一致 | 新增发送、校验、时效、重发限制、单次消费和自动登录；需要短信服务配置和可用签名模板 |
| 首版保留手机号与密码 | 可以复用现有鉴权，仍需设置和记住密码 | 改造更集中，后续再接验证码 |

若采用验证码，验证成功后按手机号查找账号：已有则登录，新号码则注册，后台管理员继续使用原有账号密码体系

验证码先完成登录验证，再保存当前草稿；验证码发送失败或过期时保留已填写的数据；开发模拟验证码与正式短信需明确区分

### 邀请码

- 继续选填，无邀请码也可进入登记流程
- 从分享链接带入的 code 在分步登记、登录跳转和刷新后仍要保留
- 新账号注册时绑定邀请来源，已注册账号不因打开另一个链接自动更换来源
- 邀请来源属于账号获客关系，不等同于父母与孩子的关系，也不等同于实际牵线人
- 当前前端仅检查六位数字就展示「已绑定介绍人」，建议改成待校验提示或显示后端验证后的邀请人

## 6. 字段设计

| 分类 | 字段 | 首版建议 |
| --- | --- | --- |
| 父母账号 | 登录手机号、您的称呼、账号状态、邀请来源 | 保留与改造现有账号字段，手机号不归到孩子名下 |
| 账号与档案的关系 | 父亲 / 母亲 | 首次登记询问，保存在账号与该档案的关系中 |
| 孩子基础条件 | 性别、出生信息、身高、现居城市、学历、月收入区间 | 作为基础登记主体，出生信息精度需明确 |
| 孩子称呼 | 昵称或称呼 | 可自动使用「某某家长的孩子」等中性显示方式，实际姓名按需填写 |
| 孩子补充条件 | 职业、婚姻状况、家乡、户籍、车辆情况、照片、特点、优势、介绍 | 后续完善，区分必填和选填 |
| 择偶偏好 | 出生年份区间、身高区间、学历下限、城市、在意的条件标签 | 支持不限和跳过，未确认的默认建议不视为用户要求 |
| 联系方式 | 家长联系手机号、微信、对外联系偏好 | 首版默认使用父母登录手机号供运营联系；更换号码需验证；对外开放另行设计 |
| 状态 | 草稿、资料完整度、审核状态、相亲状态 | 分开保存和展示，不把这些状态合成一个数字 |

当前项目已有孩子性别、年龄、身高、城市、职业、兴趣、照片和年龄/城市偏好，但它们绑定在 User 上

新增字段包括学历、收入、出生年份或生日、填写人与孩子关系、婚姻状况、家乡、户籍、车辆、特点/优势标签、身高要求和学历要求

后端启用了 DTO 字段白名单，新字段必须同步增加 DTO 校验、持久化和审核合并逻辑，只在前端增加输入项会被过滤，无法真正保存

### 字段口径

- 出生年份方便登记和长期展示，年龄可按年份估算；若要精确周岁及成年校验，需要生日或明确的边界确认，不能从年份得出精确年龄
- 不将旧的 age 直接换算成确定出生年份，保留旧年龄及采集时间并引导补填
- 收入使用区间，包含「暂不填写」，不把未填收入存为 0
- 学历用字典代码和明确的层级，便于以后筛选，不只保存自由文本
- 「特点」「优势」「对方要求」分别建标签分类，不能混入现有兴趣标签
- 未填身高、收入、择偶条件使用 null 或明确未知值，避免页面显示成真实条件
- 职业和单位性质可分开扩展，参考截图中的国企、央企属于单位性质
- 注册完成度、资料审核通过和身份认证是不同概念，不能用「审核通过」展示「已实名」

## 7. 数据结构与接口调整

建议保留 users 的登录与邀请职责，新增独立档案

```text
Account / 现有 User
  登录手机号、密码或短信登录、家长称呼、账号状态、邀请来源
          |
          | ownerAccountId
          v
ChildProfile
  孩子条件、公开称呼、相亲编号、与登记人的关系、相亲状态
          |
          +-> ProfileDraft                 编辑草稿
          +-> ProfileReview / Version      提交快照、审核记录和已通过版本
          +-> ProfilePreference            择偶偏好
          +-> ProfilePhoto / Tag           照片与标签

MatchRecord
  profileAId + profileBId + 实际介绍人/运营记录
```

上图是建议的职责划分，具体表名可沿用当前项目命名风格

首版 ChildProfile.ownerAccountId 建索引而不设置永久一对一约束，业务限制一个账号一个档案；创建接口需做到幂等，并在事务中保证并发请求不会建立两份档案

以后可放开一个账号多个档案；父母双方共同管理同一个孩子时，再增加管理关系表，不通过两个独立孩子档案来表示同一个人

父母与孩子的关系不能用现有 referrerId 表示：referrerId 是注册邀请来源，ownerAccountId 是档案归属

### 接口职责

- /me 返回父母账号信息和当前子女档案摘要，登录状态不再依赖账号上的唯一 profileStatus
- 新增档案草稿的读取与保存，保存草稿不触发审核
- 资料提交以 profileId 为对象，将完整快照进入待审核池
- 用户每次访问、修改、上传时都验证当前账号拥有该档案
- 审核通过更新孩子的已通过版本，不覆盖父母的称呼、手机号和头像
- 家长身份图片与孩子相亲照片分开，上传记录同时明确上传人和档案归属
- 牵线双方改为子女档案，邀请账号与实际介绍人保留独立含义

## 8. 草稿、审核和照片

当前页面只在已通过或已驳回状态加载资料，待审核状态会禁用表单但不加载这次提交的内容，刷新后可能出现空的只读表单

改造时需要分别提供编辑草稿、最新提交版本和已通过版本

- 未提交：恢复草稿，允许继续填写
- 待审核：展示刚刚提交的完整内容，可按明确规则撤回修改或以新版本重新提交
- 被驳回：恢复被驳回的版本并显示原因，保留用户填写的内容
- 已通过：展示已通过版本，编辑形成新草稿，新提交进入新一轮审核
- 照片选填时要同时修改前端、DTO、后端校验和审核合并逻辑，不能只改上传控件
- 用完整快照提交时，空照片数组表示明确清空；字段缺省与明确清空需要统一约定
- 上传成功先关联草稿，当前上传头像会立即更新 User，不应继续影响已经通过审核的公开档案

当前上传 URL 是直接可访问地址，不能只用前端模糊图片就宣称「解锁后才可看照片」；如后续做照片权限，需增加服务端访问控制与受控图片访问

## 10. 页面与可读性

首版建议只保留两个主导航：「孩子资料」「我的」

新增清晰的登记入口、逐步问答、资料预览、孩子资料卡和审核提示；推荐、消息等入口在能力实际完成后再增加

父母使用的页面建议采用更大的正文和触控区域，表单正文约 17-18px，主要按钮触控高度约 48-56px，重要提示不能仅靠颜色区分

评估时全局正文基准是 14px，表单标签多为 13px，需要提高核心登记页面的可读性；标题可保留品牌风格，输入内容与说明采用清楚易读的字形

每一步只问一个主题，按钮说明「下一步」「保存并继续」「提交审核」，返回后保留答案，可选项提供「暂不填写」

采用参考截图的清楚问答与大按钮交互，整体颜色与品牌样式在现有设计上调整，不机械复制竞品视觉或密集的营销弹窗

用户协议和隐私政策需有真实可打开的页面，登记时明确询问已经与子女沟通并获得同意，保存确认版本和时间；这属于产品与数据设计，不把父母勾选当成系统已经核验了子女身份

## 12. 实施顺序与验收

建议按以下顺序实施，每一步都应前后端同步

1. 使用手机号密码、爸爸/妈妈关系、出生日期与基础必填项
2. 建立账号与档案分离的数据结构，初始化独立开发库
3. 实现草稿、版本、偏好字段与档案归属校验
4. 改注册/登录引导、逐步登记、预览和「我的」页
5. 改管理端的列表、详情、审核、牵线和统计
6. 用完整流程验证后切换数据与入口

重点验收场景

- 无邀请码也能注册，有效邀请码可绑定来源，无效邀请码提示清楚
- 带 code 的链接经过逐步填写、登录、刷新后仍保留来源
- 注册成功但后续保存失败时，可以恢复草稿而不重复生成账号
- 同一账号重复提交或并发创建只产生一个首版档案
- 返回、刷新、重新登录后恢复已填写资料
- 待审核页面显示提交内容，驳回后能修改并再次提交
- 审核孩子资料不会覆盖家长称呼和登录信息
- 另一个账号无法读写或上传到该孩子档案
- 父母联系方式和孩子照片分别归属正确
- 首版照片可选、未知收入、不限偏好可通过一致的校验
- 牵线选择的是双方孩子，后台仍能找到各自家长联系人
- 原有介绍人推广与邀请关系仍可使用

## 13. 范围与后续接入

这是跨前端、后端、管理端和数据结构的中等规模业务调整，不是单页改文案

可复用 Vue/Vant、NestJS、Prisma、JWT、职业和城市字典、上传基础、管理端审核交互与日志

主要新增工作是独立子女档案、草稿和版本、更多条件字段、分步登记、后台归属展示，以及独立开发库初始化

短信验证码会再增加一个外部服务接入与验证环节，具体周期受现成短信账号、签名和模板的可用情况影响

完整复制推荐、联系解锁、会员、付费、消息、实名和运营激励，会把本次登记改造扩大为另一轮产品建设，不纳入已确认的首版范围
